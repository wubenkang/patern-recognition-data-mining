# 第 4 章 库存 —— 阅读笔记

> 第 3 章只展示了一张事实表，第 4 章把场景拉宽：用"库存"这一过程把**价值链**串起来，正式给出了 **3 类事实表**、**企业数据仓库总线架构 / 总线矩阵**、**一致性维度 / 一致性事实** 这三大主轴概念。这一章是 Kimball 方法从"建一个模型"跨到"建一套企业级集成模型"的分水岭。

---

## 一、本章要解决的问题

第 3 章的零售销售模型只覆盖了价值链最末端"卖出去"那一刻。但管理层关心的远不止销售：**采购下单 → 仓库收货 → 仓库存货 → 商店收货 → 商店存货 → 零售卖出**，每一步都会产生度量。本章要回答两件事：

1. **库存这种"水位"型业务过程，怎么用维度模型刻画？** ——引出 3 种事实表。
2. **多条业务过程如何在企业级被一致地拼起来？** ——引出总线架构 + 总线矩阵 + 一致性维度。

读完本章你应该能：

- 区分事务、周期快照、累积快照三种事实表的适用场景与各自坑点；
- 画一张总线矩阵，把组织里的业务过程梳成"行 × 列"；
- 解释一致性维度的 4 种形态（相同、缩减上卷、行子集、有限一致性）；
- 知道为什么一致性维度需要数据治理 + 高层支持，不是纯技术问题。

---

## 二、价值链与零售商案例（4.1）

价值链 = 组织主要活动的自然、逻辑流程。零售商的子集（图 4-1）：

```
向制造商发出购买订单 → 接收仓库存货 → 仓库库存产品 → 接收商店存货 → 商店库存产品 → 零售
```

每一环都对应**一个或多个事实表**。这里要建立一个全书反复出现的直觉：**操作型源系统在价值链每一步都建事务或快照**，而 DW/BI 的任务就是在每一步上挂上分析模型，并保证它们之间的维度可拼。

---

## 三、库存模型（4.2，本章的"案例三连"）

库存这件事，可以从三个不同视角建模，每个视角对应一类事实表。

### 4.2.1 库存周期快照（最常见）

业务过程：**商店每天对每个 SKU 拍一张库存照**。
4 步过程的落点：

- 业务过程 = 商店库存
- 粒度 = **每天 × 每店 × 每 SKU 一行**（注意这是周期快照特有的"维度列表"粒度，而不是事务粒度）
- 维度 = 日期、产品、商店
- 事实 = Quantity on Hand（现存数量）

最简模式（图 4-2）就是这一个事实加三个键。

#### 关键经验：稀疏性、容量、半可加性

- 周期快照是**稠密**的：即便某 SKU 当天没卖出，也要写入一行（库存就是 0 也是事实），不像事务表那样稀疏。
- 容量算给自己提个醒：60 000 SKU × 100 店 × 365 天 ≈ **22 亿行/年**。即便每行只有 14 字节，每年也要 84 MB 量级的事实表——**减少快照频率**是最直接的优化（最近 60 天保日级，更早的折成周/月级）。
- **库存余额是半可加事实**：跨产品、跨商店可加（10 个 SKU 的库存数量加起来有意义），但**跨日期不可加**（周一到周五的库存量加起来 = 5 倍周末库存毫无意义）。处理方式：跨日期取**平均值**（不是 SUM），且一定要除以"时间周期数量"。
  - 注意 SQL 的 AVG 不能直接用，因为它是**对所有行求平均**。例如 4 商店 × 7 天 = 28 行，AVG 会除以 28 而不是 7，得不到"3 商店平均日库存"。
  - 解决方案：要么 OLAP 多维数据库定义半可加聚集规则，要么 SQL 里手工除以时间周期数。

#### 增强型库存周期快照（图 4-3）

只有 Quantity on Hand 不够，常常加：

- Quantity Sold（卖出量，**完全可加**）
- Inventory Dollar Value at Cost（库存成本价值，半可加）
- Inventory Dollar Value at Latest Selling Price（库存现售价价值，半可加）

由"卖出量÷库存量"可衍生出"日供应量"、"周转率"等，而这些是**可加事实里推导出来的不可加比率**（同上一章的"分子分母原则"）。

### 4.2.2 库存事务（图 4-4）

业务过程改为仓库视角，事件粒度：

- 接收产品、入检验区、退给供应商、产品入库、出库、包装、运送、退货、删除……
- 粒度 = 每个库存事务一行
- 维度 = 日期、产品、仓库、供应商、事务类型；外加 Inventory Transaction Number 作为退化维度
- 事实 = Inventory Transaction Dollar Amount

事务事实表非常详尽，能回答任何"什么时候发生过什么"。但**只用事务事实表去重建任意时间点的库存形势在理论上可行、实际不可行**——回滚所有事务太慢、太复杂。所以才需要快照。

> 提醒：如果不同事务的"自然粒度"不同（例如有的事件涉及两个供应商），就**分多张事实表**，不要硬塞一张。

### 4.2.3 库存累积快照（图 4-5、4-6）

适用场景：**有明确开始、有明确结束、且经过一系列里程碑**的过程，例如一批产品从供应商收货 → 检验 → 入库 → 初始装运 → 最终装运。每批货**只有一行**，里程碑日期对应多个日期外键（角色扮演维度）。

这一行**会随着流程推进被反复 UPDATE**：

- 第 1 步插入：接受日期填写，其他日期外键先填默认"未知日期"键
- 第 2 步更新：检验日期填写
- 第 3 步更新：入库日期填写、入库延迟天数计算

累积快照天然适合追踪"流水线"上的进度、累计延迟、Lag。它也常带一个"状态维度"外键，用 SCD 类型 1（重写）反映流水线的最新状态。

> 注意：累积快照对 OLAP 多维数据库而言**比较麻烦**，因为它要不停修改既有行；多数 OLAP 引擎适合追加而不适合更新。

### 三类事实表对照（图 4-7，必须背下来）

| 维度 | 事务事实表 | 周期快照 | 累积快照 |
| --- | --- | --- | --- |
| 周期 | 离散事务时间点 | 有规律、可预测的间隔产生快照 | 用于已知跨度但不确定的流水线 / 工流 |
| 粒度 | 每个事务或事务行 = 一行 | 以快照周期加上其他维度 = 一行 | 每个管道事件 = 一行 |
| 日期维度 | 事务日期 | 快照日期 | 关键里程碑涉及的多个日期 |
| 事实 | 事务性能 | 时间间隔内的累积性能 | 管道事件性能 |
| 稀疏性 | 稀疏或稠密、与活动相关 | 稠密 | 稀疏，与管道事件有关 |
| 更新方式 | 不更新（除非纠错） | 不更新 | 管道活动发生时**就要更新** |

> 本章后半段反复点出："三种事实表共同构成了所有书中讲到的用例的事实类型"。任何业务过程的事实表设计，都先回答"我属于这三类里的哪一种"。

### 4.3.4 辅助事实表类型

有时事务和快照同时出现：每天追加事务影响并回滚累积快照、同时在周期快照里存 36 个月历史。这是真实项目的常态，不需要二选一。

## 四、价值链集成（4.4）

讨论完三类库存事实表后，把视角拉回价值链整体。**集成往往不是技术问题，而是组织问题**：

- 操作型系统是分别针对单一过程的孤岛，集成的责任不在源系统而在 IT。
- 集成最大障碍是高级管理层的态度——"集成要紧吗？"。**如果高层不投入资源、不强势协调，集成项目大概率失败**。
- 第 3、4 章的销售价值链事实表（图 4-8）逻辑上共享日期、产品、商店、仓库、促销等公共维度，正是集成的物质基础。

## 五、企业数据仓库总线架构（4.5，本章核心概念）

### 4.5.1 总线架构是什么

"总线"借自电子工业：所有设备插到一根标准总线上，能即插即用、互操作。
DW/BI 里的总线 = **一组标准化、共享的一致性维度 + 一致性事实**，所有维度模型严格遵守。

只要遵循总线，三件事自动成立：

1. 不同小组可以**异步并行开发**自己的维度模型，最后还能融合
2. 跨过程的查询/钻取可以做（例如把"购买订单—商店库存—商店销售"放在一张报表里）
3. 工具/数据库/平台**独立**，换 OLAP 还是关系库都不破坏总线

### 4.5.2 企业数据仓库总线矩阵（图 4-10，本章必须掌握的图）

总线矩阵是把总线架构落到一张可以贴在白板上的图：

- **行 = 业务过程**（例如：提出购买订单 / 接收仓库存货 / 仓库库存 / 接收商店存货 / 商店库存 / 零售 / 零售预测 / 零售促销跟踪 / 客户退货 / 退货给供应商 / 常客注册）
- **列 = 公共维度**（日期、产品、仓库、商店、促销、客户、雇员……）
- 单元格 = "X" 表示这个过程使用这个维度

**矩阵的几个关键作用**

- 整体规划工具：项目早期就能讨论"先做哪几行"（通常先单过程，避免一开始就做收益率这种合成过程导致 ETL 爆炸）
- 数据治理工具：列就是要被治理的核心维度
- 沟通工具：让 IT 和业务都能看懂"我们计划集成什么"

#### 4 个常见错误（图 4-10 文字部分，避坑用）

1. **基于部门的或包含太多内容的行**：行应当是"业务过程"，不是"部门"，否则会模糊掉过程视角
2. **报表中心或定义过于狭窄的行**：单业务过程支持多种分析，不要把一份报表当一行
3. **过渡泛化的列**：什么"人"维度，把员工、供应商、客户合并 → 内部地址和客户地址硬塞一起，没有好处
4. **将层次中的每个级别加入不同列**：导致蜈蚣矩阵；同一维度的层次不要拆列

### 机会/利益相关方矩阵（4.5.2.2，图 4-11）

把"列"换成业务功能/部门（销售计划、市场、商店操作、后勤、财务），告诉每个利益相关方"你关心矩阵里哪几行"。这张图特别适合作为业务沟通的入口。

## 六、一致性维度（4.6）

一致性维度 = 在多个事实表之间共享的、含义/键值/属性都相同的维度。它是总线的"物质形态"，也叫"公共维度"、"主维度"、"引用维度"。

### 4.6.1 多事实钻取（图 4-12）

钻取（drill-across）= 把多个事实表的查询结果按公共维度属性外连接起来。例如按"产品描述"列出 [订单数量, 库存数量, 销售数量]。一致性维度的最低条件是：**事实表们对接到同一份维度时，结果可以基于公共属性整齐对齐**。

### 一致性维度的 4 种形态

#### (1) 相同的一致性维度（4.6.2）

两个事实表用**完全一样**的维度表（同一物理表，或 ETL 复制出的精确副本）。所有键、属性名、属性定义、属性值都相同。这是最强一致。

> 一个维度的粒度通常下沉到最低，例如产品维度的粒度是单个 SKU。

#### (2) 包含属性子集的缩减上卷一致性维度（4.6.3，图 4-13）

两个过程粒度不同时常见。例如：

- 销售事实表粒度 = 单个 SKU
- 销售预测事实表粒度 = 品牌

这时建一份"品牌维度"作为"产品维度"的**上卷**版本：品牌维度的属性是产品维度属性的**真子集**（品牌、子类、类别、部门描述这些跨 SKU 都相同的列）。同样地，月份维度可以是日期维度的上卷子集。

> 关键：上卷维度的属性 = 基础维度属性的真子集，且属性值与基础维度严格保持一致。

#### (3) 包含行子集的缩减一致性维度（4.6.4，图 4-14）

两个维度粒度相同，但一个是另一个的**行子集**。例如公司有一份覆盖全产品的"公司产品维度"，子公司只关心"电器"或"服装"这两块——子公司维度只保留对应的产品行。

注意：与子集维度连接的事实表必须**仅包含该子集**对应的事实，否则参照完整性会被破坏，钻取出现异常。

#### (4) 总线矩阵的缩减一致性维度（4.6.5，图 4-15）

两种表达方式：

- 在矩阵元素上用"上卷文本标识"标记缩减程度（例如"日"或"月"）
- 增加额外列表示公共上卷或子集粒度

### 4.6.6 有限一致性

不是所有公司都会建企业级一致性维度——独立、自包含、互不交叉销售的子公司情况下，集成的代价可能大于收益。但**即便仅在产品描述、分类、单位这些少量公共属性上达成一致**，也已经迈出了正确方向。

### 4.6.7 数据治理与管理的重要性（这一节非常关键）

一致性维度本质上不是技术问题：

- **业务驱动的治理**：治理领头人需要来自业务、深刻理解组织运作、能平衡部门利益、有权威推动政策、强沟通能力、能"在所有人能接受的范围内不断协商达成一致"。
- **治理目标**：词汇、定义、领域值（codelist）跨业务统一。否则同一个词在每个部门含义不同，集成就只能停留在表面。
- 历史上 DW/BI 小组不愿做这件事，于是出现 ERP、MDM 等"技术解决方案"，但**技术不能替代治理**——治理是文化和地缘问题，不是 SQL 问题。

### 4.6.8 一致性维度与敏捷开发

误解：一致性维度需要先把所有维度做完才能交付，与敏捷不兼容。
实际上：

- 一致性维度允许**逐步建立和维护**，每个迭代里都不需要整个维度全打理完
- 当开发新业务过程的事实表时，**主要 ETL 工作就是关联到已经存在的一致性维度**——这是敏捷红利的来源
- 定义一致性维度需要管理共识，但**不必让每个业务用户对每个属性达成一致**（那是不现实的），从最小公共属性集开始迭代即可

## 七、一致性事实（4.7）

跨事实表对齐**KPI 命名与定义**。与一致性维度相比，事实只占工作量约 5%，但同样重要：

- 同名的 KPI 在多事实表里**必须用同样的金融定义、同样的度量单位**
- 如果定义实在不同，**就要用不同的名字**——否则用户在跨表汇总时会错误地相加不兼容的数字

#### 多度量单位陷阱

销售价值链上一个产品在仓库以"发货箱"度量、在商店以"扫描单位"度量。两条粒度不一样的事实即便都叫"sales quantity"，加起来毫无意义。两种处理：

- ❌ 在产品维度藏一个隐式转换因子，让用户自己 join 时套上去——脆弱、易错
- ✅ **事实表里同时存两种度量单位**，报表层根据需要取用

第 6 章会展开"多度量单位 / 多币种"这条专题。

## 八、本章小结（4.8 原话提要 + 我的浓缩）

- 库存的 3 种视角：周期快照（不断变化的库存场景）、累积快照（明确开始-结束的流水线）、事务（细节增强补充）。**多数项目最终是三者结合**。
- 价值链 → 总线架构 → 总线矩阵 → 一致性维度/事实，是 Kimball 方法的骨架。**任何要做企业级 DW/BI，必须坚持总线架构**。

## 九、关键术语速查

| 术语 | 一句话解释 |
| --- | --- |
| 价值链 | 组织主要活动的自然、逻辑流程；矩阵的"行"来源 |
| 周期快照事实表 | 固定间隔拍照，粒度 = 维度列表；稠密、半可加 |
| 库存事务事实表 | 每个库存事件一行；详细、稀疏；不便重建任意时点 |
| 累积快照事实表 | 一行代表一条流水线/工作流；多日期外键；**会被 UPDATE** |
| 半可加事实 | 跨某些维度可加，**跨日期不可加**（如库存余额、账户余额） |
| 总线（Bus） | 借自电子总线的标准接口隐喻 |
| 企业数据仓库总线架构 | 增量式、架构化的企业 DW/BI 建设方法 |
| 总线矩阵 | 行=业务过程，列=公共维度，X 标记参与；规划/治理/沟通三合一工具 |
| 机会/利益相关方矩阵 | 把列换成部门/职能，匹配业务方关心的过程 |
| 一致性维度 | 多事实表共享、键值/属性/含义都对齐的维度 |
| 缩减上卷一致性维度 | 公共属性的真子集，对应高粒度事实（如品牌、月） |
| 行子集一致性维度 | 同粒度但只保留部分行（如子公司只看电器） |
| 一致性事实 | 跨事实表对齐 KPI 名称、定义、金融含义、度量单位 |
| 数据治理 | 让一致性能落地的组织能力，不是技术 |

## 十、读完本章应该能做的事

1. 拿到一个新业务过程，能立刻判断它该用三类事实表中的哪一类（或哪两类组合），并解释为什么。
2. 看到任何"余额、水位、当前值"型指标，立刻识别为半可加，并知道跨日期要用平均、不能 SUM。
3. 给自己的工作领域（电商、广告、风控、推荐都行）画一张 5–10 行 × 5–10 列的总线矩阵，并能对每个 X 解释一下"是不是真的需要"。
4. 区分三种一致性维度形态，并能对一份具体设计判断它是相同、上卷还是行子集。
5. 看到"产品销量为什么对不上财务报表的销售额"这种问题，能立刻怀疑一致性事实没对齐（命名/定义/度量单位）。
6. 看到一致性问题，先想"治理 + 高层 + 业务领头人"，再想"工具 + ETL"。

## 十一、与第 3 章的衔接、对第 5 章的预告

- **承接第 3 章**：零售销售模型只是总线矩阵的 1 行；本章把它放进价值链上下文中，给出库存这一行，并把"两条事实表如何拼"这件事正式讲清楚。
