# 第 3 章 零售业务 —— 阅读笔记

> 本章是全书最经典的入门案例。Kimball 用一家拥有 100 个分店、单店约 60 000 个 SKU 的食品杂货连锁来串起整套维度建模方法，读完应当能独立画出一个 POS 销售星型模型，并理解每个设计选择背后的取舍。

---

## 一、本章要回答的核心问题

为什么不直接照搬 OLTP 的表结构去做分析？因为业务用户问的是"销售在不同维度上的结构和趋势"，而不是"某一行交易记录长什么样"。本章要解决的就是：把一笔笔零碎的 POS 交易，转换成业务用户可以"切片、切块、下钻、上卷"的星型模型。

学完后能掌握三件事：

1. **维度建模的 4 步过程**（选业务过程 → 声明粒度 → 确定维度 → 确定事实），这是贯穿全书的方法论。
2. **零售 POS 销售模型**这一最经典的星型示例，从此能识别"事实表 + 多个维度表"是什么样子。
3. **几类典型维度技术**：日期维度、产品维度、商店维度、促销维度（因果维度）、退化维度（POS 事务号）、雪花、支架、蜈蚣事实表。

---

## 二、4 步设计过程（3.1 节，本章主干）

### 步骤 1：选择业务过程

业务过程 = 组织完成的一项原子级业务活动，例如下订单、开票、收款、处理保修。它有几个共同特征：

- 通常用动词表示，是真实在发生的活动，与之相关的维度描述事件触发时的环境。
- 由源操作型系统支撑（POS、ERP、CRM 等），简单或购买系统都算。
- 输入是某些维度的输出。一连串过程会产生一连串事实表。

设计原则：**站在业务过程角度建模，而不是站在部门或业务功能角度**。同一份订单数据如果按部门分别建模，会出现多套不一致的口径；按过程建模就能在企业层面共享一致的事实。

> 本章选择的业务过程是 **POS 零售交易**。这是该连锁店最关键、最易实现、且最贴近"客户购买情况"的过程。

### 步骤 2：声明粒度

粒度 = 事实表的每一行表示什么。它必须用业务术语表达，例如：

- 客户销售事务上的每个产品 → 一行
- 医生开具的票据列表内容 → 一行
- 机场登机口处理的每个登机牌 → 一行

> 本案例的粒度声明：**POS 交易票据上的每个产品，单一项目上卷的所有销售记一行**。

为什么坚持选最细的"原子粒度"？

- 原子粒度有最强的多维性，能拼出未来任何尚未预想的查询。
- 一旦声明的是"日 × 商店 × 产品"这样的汇总粒度，就再也回答不了"某客户当晚买了几样商品"这种细节问题。
- 详尽的事实就像沙土，可以堆出任意形状；汇总的事实就像砖块，只能砌固定的墙。

教训："如果不能清楚地定义粒度，整个设计就像建立在流沙之上"。如果发现第 3 步、第 4 步走不下去，往往意味着第 2 步的粒度声明错了，要回头重新声明。

### 步骤 3：确定维度

维度回答"业务人员如何描述本次度量事件的数据"。一旦粒度清晰，维度就比较直接：与"谁、什么、何处、何时、为何、如何"相关的实体，都是候选维度。

本案例围绕 POS 销售选定的维度：

- **日期维度**：何时
- **产品维度**：什么
- **商店维度**：何处
- **促销维度**：为何（因果维度，3.3.4）
- **收银员维度**：谁（操作员）
- **支付方式维度**：如何
- **POS 事务号**：作为退化维度（3.3.6），不单独建表

设计要点：维度表中应当有具体的、文本类型的属性，越多越好——它们才是 BI 报表行头和过滤条件的来源。

### 步骤 4：确定事实

事实回答"过程的度量值是什么"。事实必须与粒度一致；不同粒度的事实必须放进不同事实表。

本案例（图 3-3 零售销售事实表）记录的事实：

- Sales Quantity（销售数量）
- Regular Unit Price（标准单价，可加性差，常做不可加事实候选）
- Discount Unit Price（折扣单价）
- Net Unit Price（净单价）
- Extended Discount Dollar Amount（扩展折扣额 = 数量 × 单位折扣额）
- Extended Sales Dollar Amount（扩展销售额 = 数量 × 净单价）
- Extended Cost Dollar Amount（扩展成本额）
- Extended Gross Profit Dollar Amount（扩展毛利 = 销售额 − 成本额）

#### 事实的三类分类（重要）

| 类别 | 含义 | 例子 | 处理建议 |
| --- | --- | --- | --- |
| **可加事实** | 在所有维度上都可以求和 | 销售数量、扩展销售额、扩展成本、扩展毛利 | 优先存储，最灵活 |
| **半可加事实** | 在部分维度上可加，例如时间维度上不可加（库存量按天累加无意义） | 库存余额、账户余额 | 用平均/快照处理，下一章库存案例会展开 |
| **不可加事实** | 任何维度上求和都没意义，例如比率、单价、百分比 | 利润率、单价、转化率 | **存分子分母两个可加事实，BI 工具在汇总后再算比率**；不要直接存比率 |

关键经验：**利润率不要直接存事实表里**。如果要算分类下的利润率，应该把"销售额"和"成本额"分别求和后再相除，而不是把每行的利润率简单相加。

#### 事务型事实表的特征（本案例就是这种）

- 粒度是一个事务事件，例如一行 = 一个事务/一行项目
- 行可能比较稀疏，因为不是所有产品每天都被销售
- 表会非常庞大，数十亿行常见
- 事实通常都是可加的；只要数量×单价能扩展出来，就尽量不要只存单价

## 三、零售业务案例研究（3.2 节）

### 业务背景

- 食品杂货连锁，5 个州、100 家分店
- 每店约 60 000 个 SKU
- 数据来源：POS 收银机（图 3-2 票据样例）、供货商发货
- 管理目标：在订单 / 库存 / 销售上做利润最大化，决策与价格、促销有关
- 报纸广告 / 终端展示 / 礼券等促销手段一旦降价 50 美分，毛巾这类商品销量可上升 10 个百分点，但纸巾本身可能是亏本销售品

### 4 步过程在本案例的落地

- 第 1 步：选 POS 零售交易
- 第 2 步：声明 POS 交易票据 × 单产品的最细粒度
- 第 3 步：确定日期、产品、商店、促销、收银员、支付方式六大维度，加 POS 事务号退化维度
- 第 4 步：确定数量、4 类金额（销售、扩展销售、成本、毛利）等事实

## 四、维度表设计细节（3.3 节，必看）

### 3.3.1 日期维度（每个维度模型几乎都要有）

日期维度有几个特别之处：

- **可以提前生成**：20 年也只有约 7 300 行，相对很小
- **必须做成有真实属性的维度表，而不是用 SQL 函数**——SQL 不直接支持"工作日"、"假日"、"财务期"、"季度"等过滤
- 推荐属性（图 3-4，记关键属性即可）：Date Key (PK)、Full Date Description、Day of Week、Day Number in Calendar Month/Year、Day Number in Fiscal Month/Year、Last Day in Month Indicator、Calendar Week/Month/Quarter/Year、Fiscal Week/Month/Quarter/Half Year/Year、Holiday Indicator、Weekday Indicator、SQL Date Stamp

设计要点：

- 标识列要有意义的文本（例如 Holiday / Non-Holiday），不要用 1/0、Y/N、True/False，否则用户报表里全是难以解读的代码
- 当前与相对日期属性（IsCurrentDay、IsCurrentMonth、IsPrior60Days）会随时间变化，每次加载更新
- 对于 time-of-day（当天时间），如果有粒度更细的需求，单独建一个"当天时间"维度，与日期维度分开

### 3.3.2 产品维度

- 描述每个 SKU，行数 = 几万到几百万
- **扁平化多对一层次**：一个 SKU 上卷到品牌，品牌上卷到类别，类别上卷到部门——把这条层次链上的所有属性都直接放在产品维度里，**不要因为"重复"就规范化**（图 3-7、3-8）
- 重复的低粒度属性留在主维度表里，是基本维度建模技术，目的就是简化和高性能
- 维度属性可有 50 个左右，每个属性都是约束、行头、下钻指针的来源

#### 内嵌含义的属性

操作型代码常常本身就有内嵌含义（前 4 位代表类别，第 5–9 位代表制造商等）。设计时**保留原码作为整体属性，再把分解后的字段也一并展开**。

#### 数字值是属性还是事实？

判断方法：

- 主要用于**计算**（参与汇总的扩展额）→ 放事实表
- 主要用于**约束 / 分组 / 标识**（标准价格用于过滤）→ 放维度表
- 既要计算又要分组，就**两边都放**——同一份数字在事实表里是事务时的价格，在维度表里是当前的标准价格

### 3.3.3 商店维度

- 主要的地理维度
- 包含多层次：邮编 → 城市 → 县 → State；以及内部组织：商店 → 街区 → 地区
- 因为美国不同州可能有同名城市，所以维度里需要 City-State 这种组合属性来唯一识别
- 数字属性 Selling Square Footage（卖场面积）虽然理论上跨店可加，但因为通常用于约束/分组，**放维度表更合适**

样例属性：Store Key (PK)、Store Number (NK)、Store Name、Store Street Address、Store City、Store County、Store City-State、Store State、Store Zip Code、Store Manager、Store District、Store Region、Floor Plan Type、Photo Processing Type、Financial Service Type、Selling Square Footage、Total Square Footage、First Open Date、Last Remodel Date 等。

> First Open Date / Last Remodel Date 是日期类型，可以直接放维度，但若要按"非标准日历日历属性"（财务周期、假日）分析，可建立一个**视图**指向日期维度（即"日期角色扮演"概念，第 6 章再细讲）。

### 3.3.4 促销维度（因果维度，最有趣的维度）

促销条件包括降价、终端通道展示、报纸广告、礼券，是"为什么发生销售"的因果维度。促销分析回答的问题：

1. 促销期间销量比基本销售提升多少（提升）
2. 促销前后是否有"销售转移"（侵蚀）
3. 同类产品中没参与促销的是否被偷走销量（销售侵蚀）
4. 促销分类是否带来净增（市场增大）
5. 促销是否真的盈利（利润 vs. 侵蚀）

设计选择：把降价、广告、展示、礼券这 4 类条件**合并到一个促销维度**还是建 4 个独立维度？书中建议**合在一起**，原因：

- 4 类机制经常高度关联，合并维度行数不会比任一单维度大很多
- 合并后可在浏览时直接看到组合效果（哪些产品同时上了广告 + 降价 + 展示）
- 缺点：如果 4 类机制需要单独管理，分开更直接——选择取决于业务

样例属性：Promotion Key (PK)、Promotion Code、Promotion Name、Price Reduction Type、Promotion Media Type、Ad Type、Display Type、Coupon Type、Ad Media Name、Display Provider、Promotion Cost、Promotion Begin/End Date。

#### 关于"未促销"产品 → 引出**无事实的事实表**

POS 事实表只记录"卖出去了什么"，但管理层最关心的恰恰是"被促销但没卖出去的产品"。如果在产品维度上添加 0 销量行，事实表会爆炸。正确做法是建一张**促销范围事实表**（图 3-14），粒度为"促销期 × 商店 × 促销中产品"，无论是否售出都记一行。两表做差集，就能算"什么没卖出"。

### 3.3.5 其他零售业维度

- 收银员维度：和商店维度类似，可建出纳员维度，包含员工属性。自助结账无对应出纳员
- 支付方式维度：维度行 = 现金、信用卡、礼券等。如果一笔交易支持多种支付方式，那粒度就要么改"每个产品每种支付方式一行"，要么把支付方式拆出独立事实表

### 3.3.6 退化维度（DD）

POS 事务号最特别——它的所有属性已经被其他维度（日期、商店、收银员）拿走了，但事务号本身仍然有用：它能把一张票上的所有产品聚成一个"市场购物篮"。

处理方式：**把它直接放在事实表里，不建对应维度表**，称为退化维度。除了 POS 事务号，订单号、发票号、提货单号、保单号都常见为退化维度。退化维度通常是事实表的主键组成部分。

## 五、空键、空属性和空事实

- **不要在事实表外键列上用空键**，参照完整性会出问题；为"未促销"配一行特殊键（如 0 或 −1）
- 维度属性值未填时，用 "Unknown" 或 "Not Applicable" 替代空字符串，否则报表分组结果不一致
- 事实里偶尔可有空值，聚集函数 SUM/MIN/MAX/COUNT/AVG 会跳过空，但 0 会被算入

---

## 六、零售模式的扩展能力（3.5 节）

模型设计完几年后，业务变了怎么办？只要按 4 步过程走，扩展是平滑的：

- **新维度属性**：直接加列；如果是有时间点意义的属性变化，要按缓慢变化维度处理（第 5 章）
- **新维度**：在事实表加外键、加新的维度表
- **新可度量事实**：直接加列，老行用空填充；新事实粒度不同，应建独立事实表

> 整个核心是：**始终保持最细原子粒度 + 一致性维度**，未来扩展才不会撞墙。

## 七、维度与事实表键（3.7 节）

### 维度表代理键（强烈推荐）

代理键 = 无意义的整数序列，从 1 起编号；维度表主键 **不要** 用源系统自然键。原因有 6 点：

1. **缓冲源系统变化**：源系统重排自然键（休眠 12 月后回收）也不影响仓库
2. **集成多源**：多源系统下自然键不一致，代理键提供统一公共主键
3. **改进性能**：4 字节整数能表示 ±20 亿，比拼接字符串小得多，连接更快
4. **处理空或未知条件**：可分配特殊代理键给"未促销/匿名客户"
5. **支持维度属性变化跟踪**：SCD 类型 2 用同一个自然键多个代理键来表示不同时间快照（第 5 章重点）
6. **统一日期维度键**：YYYYMMDD 整数主键易读，但代理键能更安全处理"未应用日期"等空场景

### 维度自然键 / 持久键 / 超自然键

- 自然键 NK 仍然要保留，作为维度表的一个属性
- 一个实体在多个源系统里有多个自然键时，要建立"持久标识符"（不变的超自然键）来跟踪同一实体跨系统的统一身份

### 退化维度的代理键

通常退化维度（POS 事务号）不需要代理键，但跨多个本地系统、有重号风险时可建一个。

### 日期维度的智能键

日期维度可用 YYYYMMDD 智能整数键，便于分区与冷热分离；但要注意整数键直接查询时不要绕过日期维度，否则会失去"工作日 / 假日"等过滤能力。

### 事实表代理键

事实表通常**不需要代理键**，因为事实表主键 = 几个维度外键 + 退化维度。但有几种情况会让事实表代理键带来好处：

- **直接唯一标识**单行
- **加载失败后恢复重启**：用代理键能精确知道断点
- **替换更新**：先插新行，再删旧行，避免直接 UPDATE 的事务复杂性

## 八、抵制规范化的冲动（3.8 节，重要立场）

来自规范化建模背景的人会本能想把维度规范化（雪花化）。Kimball 立场：**不要这么做**。本章讨论 3 种结构：

### 雪花模式（不推荐）

把产品维度的部门描述等冗余字段拆出去（图 3-15 产品维度雪花化）能省一点存储，但代价：

- BI 用户写复杂多表 join，不易理解
- 查询优化器选错执行计划风险更高
- 节省的磁盘空间相对事实表 10GB 量级几乎可以忽略
- 对位图索引、扁平浏览能力都有负面影响

> 维度表的存储相比事实表小几个数量级，**省那一点空间不值得**。

### 支架表（特殊场景才用）

如果某个维度内附加的子维度自身有一组完整的属性（比如产品维度内挂一个"产品引进日期"维度，要按非标准日历分析它），可以建支架表（图 3-16）。但要克制：**支架不易理解，限制了在单一维度中浏览属性的能力**。原则上不要大量使用。

### 蜈蚣事实表（错误模式，要警惕）

有的建模者把每个层次都拆成独立维度，结果一张事实表挂上 20 多个维度（图 3-17：日维度、周维度、月维度、季度、年、商店、商店所属州、商店所属区、商店建筑平面图……）。这就是**蜈蚣事实表**——100 条腿的怪物。

设计准则：

- 多数业务过程的事实表应当**用不超过 20 个维度**
- 如果设计有 25 个以上维度，先想能不能合并相关维度
- 同一层次的元素当作不同维度，是维度建模最常见的错误

## 九、关键术语速查表（背下来）

| 术语 | 一句话解释 |
| --- | --- |
| 业务过程 | 组织内一项原子级活动，建模的起点 |
| 粒度 | 事实表每行表示什么；必须用业务语言声明 |
| 原子粒度 | 最细级别的粒度，灵活性最高，本章和全书首选 |
| 事实表 | 存放业务过程度量值的表；可加事实首选 |
| 半可加 / 不可加事实 | 部分维度上不可加 / 任何维度上不可加（存分子分母让 BI 算） |
| 维度表 | 描述事实环境的"谁/什么/何处/何时/为何/如何" |
| 退化维度 (DD) | 没有对应维度表、直接放在事实表里的业务键，如 POS 事务号 |
| 因果维度 | 解释"为什么发生"的维度，例如促销 |
| 雪花 | 把维度规范化拆表，**不推荐** |
| 支架表 | 维度内挂一个子维度，**慎用** |
| 蜈蚣事实表 | 一张事实表挂 20+ 个维度，**反模式** |
| 代理键 | 无意义整数主键，仓库主键的标准做法 |
| 自然键 NK / 持久键 | 操作系统里的业务键，仓库里降为属性 |
| 无事实的事实表 | 记录"事件发生 / 覆盖范围"但没有数量度量的事实表 |

## 十、读完本章应该能做的事

1. 给一个新业务（例如自家电商订单），独立完成 4 步过程：业务过程 → 粒度 → 维度 → 事实，并能讲清每步为什么这样选。
2. 画出一张星型图，事实表挂 5–7 个维度表（含退化维度和因果维度），能解释每个维度为什么不规范化。
3. 区分某个数字到底应该进事实表还是维度表（看是参与汇总还是参与过滤）。
4. 看到比率/百分比类指标，立刻想到"存分子分母，不存比率"。
5. 一眼识别出蜈蚣事实表反模式，并能合并同层次维度。
6. 看到"还想分析没卖出去什么"这类问题，能想到无事实的事实表 + 差集这条解法。

## 十一、与第 1、2 章的衔接，与第 4、5 章的预告

- **承接**：第 1 章给概念，第 2 章给术语清单，本章把它们落到一个完整可运行的模型上。
- **下一章（第 4 章 库存）**：会引入**周期快照事实表**和**累积快照事实表**，并第一次正式讲企业级**总线矩阵**——本章的 POS 销售只是总线矩阵中的一行。
- **第 5 章 采购**：正式讲 SCD（缓慢变化维度）类型 0–7，本章只是埋下伏笔。

> Kimball 在小结里强调：**清楚地声明粒度 + 获取最原子级数据 + 健壮的描述性维度属性**——这三点是维度建模长期成功的核心，比任何技巧都重要。
